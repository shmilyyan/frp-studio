# 设备接力发现、恢复与反馈改进设计

> 日期：2026-09-28  
> 状态：设计已由用户确认；待规格审阅  
> 范围：FRP Studio Windows 端与 iOS Handoff 客户端

## 目标

改善设备接力的连接恢复和即时反馈：Windows 服务主动发现 iOS 设备并在管理界面展示；iOS 默认自动重连，并在启动或回到前台时恢复所有已配对的历史 Windows 服务端；剪贴板发送和接收都给出明确结果，避免用户无法判断内容是否已同步。

## 当前问题与原因

1. Windows HandoffService 已定时查询 `_handoff._tcp.local`，并能从 iOS Bonjour TXT 记录中识别设备，但扫描结果只更新已配对设备的可达状态，并通过 socket 事件通知管理员。设备管理页没有独立的局域网发现设备视图。mDNS 响应里的 SRV target 与 A 记录 owner 未正确关联时，地址会退化为 `0.0.0.0`；扫描以固定 1 秒窗口判定离线，容易受慢响应和扫描重叠影响。
2. iOS 的 Socket.IO 已启用断线自动重试，但启动恢复逻辑只连接一个 Keychain 中的 `handoff_base_url`。已保存的 `pairedDevices` 列表没有被逐台恢复；Bonjour 发现也没有自动匹配已配对设备并刷新它的地址。界面当前用是否存在 `baseURL` 判断连接状态，因此已保存地址可能显示为在线。
3. 两端的剪贴板路径多半只写日志、剪贴板或历史记录。Windows 接收 iOS 内容后没有及时发给主界面；iOS 收到推送或手动拉取后仅更新剪贴板和页面预览。Socket.IO 发送没有写入确认，无法区分发出与服务端成功写入。

## 设计

### 1. 服务端发现与展示

- HandoffService 持续主动查询局域网 Bonjour 服务，维护短期发现列表。每个发现项包含稳定 `deviceId`（若存在）、名称、平台、host、port 和 `lastSeen`；地址解析从 SRV target 关联 A/AAAA 记录，而不是用服务实例名匹配地址记录。
- 扫描周期和响应收集窗口彼此分离：一次扫描有明确开始与结束，不能因迟到的上一轮回包误判离线；手动刷新会立即发起扫描。发现项在多个扫描周期未出现后才变为离线/过期。
- 发现项经现有主进程 IPC/Socket.IO 事件更新到 Windows 管理界面的独立“局域网发现”列表。已连接状态仍以已认证的 Socket.IO peer 会话为准，mDNS 只表示设备可达。
- Windows 服务不能仅凭 Bonjour 广播建立 iOS 客户端会话。发现不自动配对、不授予信任，也不伪装成已连接；iOS 端负责发起到 Windows 服务端的连接。
- Bonjour 不可用或被网络隔离时，保留已有二维码/手动连接路径，并清楚显示发现状态。

### 2. iOS 自动连接与恢复

- 用设备 ID 维护独立 Socket.IO 连接和状态，避免单一 `baseURL/currentDeviceId` 代表所有已配对服务器。
- 默认开启自动恢复。应用启动和回到前台时，对本地持久化的每台已配对 Windows 服务端启动或恢复连接；发现同一 `deviceId` 的 Bonjour 项时，优先使用新 host/port，发现暂时不可用时回退到该设备保存的地址。
- 每台服务器各自显示连接中、在线、重连中或离线状态。Socket.IO 自动重试负责单连接断线恢复；应用生命周期负责重建进程级连接。对同一设备复用连接并限制并发尝试，防止重复 socket 和状态互相覆盖。
- 只自动重连已配对设备。新发现的服务仍需用户通过现有配对/连接流程确认；不得把未经认证的 Bonjour TXT 当作身份凭证。

### 3. 剪贴板确认与用户反馈

- 各种剪贴板入口（iOS 自动监听、手动发送、服务端推送、手动拉取，以及 Windows 本地监视/接收）收敛到统一的发送与接收处理路径，保持现有空内容过滤、本地复制保护和内容去重。
- iOS → Windows：Socket.IO `clipboard` 发送使用 ACK；服务端仅在成功写入 Windows 剪贴板后返回成功，失败时返回错误。iOS 据此反馈“已同步”或可理解的失败原因，不把 emit 本身当成成功。
- Windows → iOS：服务端给每次新内容分配传输 ID。iOS 成功写入系统剪贴板后回送接收确认；Windows 收到确认后，在主界面反馈已送达的设备。iOS 接收后也显示短暂的“来自设备，已复制到剪贴板”提示。
- Windows 桌面和 iOS 前台用应用内短暂提示；手动操作也显示明确的成功/失败结果。无需新增系统通知权限请求。
- 反馈载荷只包含传输 ID、方向、设备名、内容长度和结果，不含剪贴板正文。相同 hash/传输 ID 经 socket、轮询或重连重复抵达时只写入、提示一次。

## 不在本次范围

- 通过 mDNS 自动信任或配对新设备。
- 改造跨网/FRP 中继连接协议、增加 iOS 后台常驻能力或申请系统通知权限。
- 替换现有 SQLite 传输历史存储方案。

## 验收标准

1. Windows HandoffService 启动后会主动发现 iOS Bonjour 设备，管理页显示设备名、可达状态和最近发现时间；手动刷新立即触发新扫描。无 Bonjour 地址时不显示虚假的 `0.0.0.0` 可连接项。
2. 已配对服务器均从 iOS 本地历史列表恢复；应用启动/回前台以及断线后均会自动连接或重试。新发现的地址能更新对应服务器；一个服务离线不影响其他设备状态。
3. iOS 本地发送剪贴板时，用户能分辨服务器确认写入、仍在重试和失败；接收服务端内容后，系统剪贴板更新且用户看到一次提示。Windows 发出的内容收到 iOS 写入确认后，Windows 界面也反馈目标设备。
4. 自动发现不等于配对；未配对设备不被自动连接为可信设备。重复事件不会造成重复写入或提示，反馈不显示剪贴板正文。

## 实施切分建议

1. Windows Bonjour 发现数据模型、地址解析、扫描生命周期与管理界面展示。
2. iOS 按设备的自动连接/启动恢复与连接状态模型。
3. Windows/iOS 剪贴板 ACK、送达回报及两端即时反馈。
4. 集成审查：协议兼容、发现/连接状态语义、重复消息和失败路径。
